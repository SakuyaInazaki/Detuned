- `packages/server/src/app.ts:167–175` constructs plain HTTP Fastify without forceCloseConnections and without the TLS socket tracker. Nothing in the receipt establishes a stuck business poll.
- Installed **Fastify 5.12.5**, `packages/server/node_modules/fastify/lib/server.js:127–139`, chooses default `forceCloseConnections='idle'` when Node supplies closeIdleConnections. `fastify.js:389–418` runs application preClose **before** closing HTTP. Completion ultimately depends on the `instance.server.close(callback)` callback at :418–424. An active / incomplete HTTP connection is not made closed merely because fetch rejected or a client-side task settled.
- Installed `lib/config-validator.js:15–25,1265` defaults connectionTimeout=0, requestTimeout=0, keepAliveTimeout=72000; `lib/server.js:338–341` applies these to the HTTP server. Therefore this fixture has no short connection/request timeout that proves transport cleanup within 2s. The 72000 default is not evidence that this specific connection was an idle keepalive, nor proof it is the sole cause.
- `packages/cli/src/serve-shutdown.ts:26–30` deliberately requires closeApp before closing DB/releasing lock; its watchdog reports failure and exits, rather than declaring an unfinished close successful. `packages/cli/src/index.ts:392–395` delegates to the same app.close. We should preserve that ordering, not copy the fixture's diagnostic DB cleanup into a production success path.
