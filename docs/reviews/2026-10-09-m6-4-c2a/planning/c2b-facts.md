# C2B bounded source facts — no architecture selection

Static read only, based on current C2A source plus sealed C1 `planning/c2-facts.md` and `c2-visibility-facts.md`. No product/DDL edits, schema execution, checks, generated files or environments were run. C1 reports' knowledge-status paragraphs describe the pre-C2A source and are superseded by C2A source; their public-search/privacy facts remain applicable. This report enumerates cost and missing existing hooks, not a chosen design.

## 1. Current public-read privacy contact points

`packages/server/src/routes/reviews.ts` routes GET `/spaces/:space_id/review-submissions/:id` to module `ReviewSubmissionService.getSubmission`; GET request submissions routes to `listVisibleSubmissions`. Module `modules/review/src/submission-service.ts:getSubmission` holds `storage.readSnapshot`, calls refreshed current observer/read auth, then rejects an inaccessible request or a row that is neither the current actor's own submission nor `revealed_at!==null`. List first establishes snapshot material visibility, iterates the fixed assignments and calls the same reader for visible rows.

The record/online checks already live in core and are imported by the review module:

- `packages/core/src/services/review-submission-records.ts:validateReviewSubmissionRecords` validates payload, assignment/request/session/version/snapshot bindings and complete all-assignment reveal consistency. A revealed flag alone is not its whole proof.
- `review-request-records.ts:readReviewSnapshotRecords` applies current online privacy to target/dependencies/public snapshot artifacts, retaining historical fixed refs. Intrinsic variants are separate and must not replace online privacy.
- `review-submission-records.ts:assertReviewSubmissionPostEvidencePrivacy` validates post evidence ownership/scope/revision and rejects redaction.
- `review-artifact-access.ts:assertStoredSubmissionEvidencePrivacy` revalidates the submission/snapshot then all post/artifact evidence, including private assignment/owner binding. `assertStoredSubmissionEvidenceReady` adds fresh readiness and is explicitly not a historical-read rule.
- `review-artifact-access.ts:assertReviewArtifactReadAccess` permits a non-owner private artifact only after its owning assignment has a revealed submission that explicitly references it; unused private uploads stay private.

These helpers are core exports (`packages/core/src/index.ts`); core does not import the review module. There is no current single core helper meaning “revealed-only public search submission”. The module read gate intentionally includes own sealed rows, so calling it unqualified from search would not implement public-only visibility. Historical cancelled/stale/accepted/rejected requests remain readable after reveal subject to privacy; revision/policy changes or withdrawal alone are not the current reader's redaction rule. Search access must still refresh ACL, and no existing helper turns a submission into a post identity.

## 2. Reveal and redaction transactions; reverse lookup gaps

`ReviewSubmissionService.submit` outer `storage.transaction` performs authorization/assignment/session/snapshot/current-evidence checks and `IdempotencyService.executeIdempotent`. Before the final required submission it validates every prior row's post evidence, general privacy and fresh readiness. Inside the same tx: `updateReviewRequest` creates the request-version record with phase collecting/revealed; `createReviewSubmission` stores the new payload; private `review.submitted` event is appended; on all-complete, `revealReviewSubmissions(requestId,now)` stamps all rows and public `review.revealed` is appended. Idempotent result shares this transaction. SQLite methods are in `packages/storage-sqlite/src/sqlite-storage.ts` near 1617–1638; reveal is one UPDATE by request_id and there is no opinion-search write.

`packages/core/src/services/redaction-service.ts:createRedaction` uses `IdempotencyService.executeIdempotent`'s transaction, rechecks target, determines artifact public/private scope, invokes storage `createRedaction`, optionally `markReviewRequestsStale` for a post or public-space artifact, appends scope-correct event and saves result. SQLite `createRedaction` near 1431–1524 uses a nested transaction: post lifecycle becomes redacted, every post revision is sanitized (including tags/structured), post_fts rows are deleted and matching legacy idempotency content sanitized; artifact state becomes redacted. Revealed private evidence artifact redaction uses the same artifact transaction but private event and no public-material stale hook. Existing read privacy still rejects it.

`StoragePort.listActiveReviewRequestsForMaterial` has SQL near 1653: only phases collecting/revealed; post material uses snapshot_items target_post/dependency_post; artifact uses snapshot_items artifact; policy uses all active requests in the space. `snapshot_items_material_idx(item_type,item_id,snapshot_id)` exists. This is a useful existing reverse lookup but excludes historical accepted/rejected/changes_requested/cancelled/stale requests, and does not include submission evidence. `listReviewSnapshotItems(snapshotId)` only scans forward by snapshot.

`review_submissions.payload_json` holds evidence_refs; no normalized evidence-reference table/index, no reverse port for post/artifact evidence, no bounded space-wide revealed-submission candidate port, and no historical all-phase material reverse port exists. Existing ports find a submission by ID/assignment/session and list rows for one request. Raw JSON SQL could locate evidence, but no existing contract/hook makes it bounded or reusable. A private evidence redaction must cover both the submitted owning assignment and any affected publicly revealed payload without exposing the otherwise sealed row. No current index deletion hook covers that case.

## 3. Search contracts and explicit source compatibility contacts

`packages/protocol/src/search.ts` SearchQuerySchema is strict `{q,kind?,tags?,thread_id?,limit?,cursor?}`. SearchFilterSchema is strict kind/tags/thread_id. q trims to 1–256 code points; tags JSON <=8192 bytes and <=100 unique tags; limit1–100; cursor<=4096. SearchResultItemSchema is strict post-only `{post_id,revision,thread_id,kind,title,summary,tags,snippet,created_at}`; SearchPage uses array data plus `{truncated:false,next_cursor}`. No formal-submission identity DTO/union/page guard exists.

`server/src/routes/search.ts` independently allowlists q/kind/tags/tags_json/thread_id/limit/cursor; source currently fails its allowlist. It maps transport tags_json losslessly, validates normal kinds and calls core SearchService.search. That service refreshes observer ACL, normalizes query, obtains signed cursor, calls searchPosts with candidate cap5000, applies encoded item bytes cap262144 and returns signed continuation. Current post search storage holds a read transaction around preflight+page; >=3-codepoint query uses quoted phrase post_fts MATCH and its match candidates, shorter LIKE path counts property-filtered candidates before text scan; returns active current-revision posts, ID DESC, limit+1. These are candidate/encoded output budgets, not CPU/SQLite VM time bounds.

`core/services/search-cursor.ts:searchQueryHash` binds q, normalized kind/thread/tags and id_desc, not a source. Cursor is strict `{v:1,purpose:'search',actor_id,space_id,query_hash,sort:'id_desc',before_id,exp}` with one-day expiry. Supporting an explicit review_submissions source requires a cursor source discriminator or equivalent source-bound hash. Adding `source:'posts'` unconditionally to the old hash would change existing omitted-source cursor identity; existing schema only accepts v1/current fields. Review sorting/ref interpretation cannot simply reuse post before_id without deciding that binding.

`packages/client/src/client.ts:search` has fixed `Promise<SearchPage>` post result, forwards q/kind/tags_json/thread/limit/cursor, and only static-casts response. `callTool:forum_search` forwards params.q and nested filters; source is not forwarded. `protocol/src/tools.ts:ToolSearchParamsSchema` is strict q/filters/limit/cursor; `forum_search` remains one existing tool name. MCP/Pi expose canonical tools/shared client rather than alternative search SQL. CLI `packages/cli/src/index.ts` search options --space/--query/--kind/--tags/--limit/--page/--cursor/--thread forward to shared client; source is not an option.

An additive explicit source can leave omitted/default posts row shape and parameter behavior unchanged, but requires changes to strict query/allowlist/tool schema and caller forwarding; old strict servers/tools reject the new parameter. A generic union SearchPage return can change existing TypeScript post consumers even when runtime default remains post-only; overload/generic/type decision belongs to root. A review-result DTO must carry real submission/request/snapshot/fixed-target identity, not post_id fabricated from submission ID. Meaning of post filters kind/tags/thread for review source, and invalid source/filter combinations, is currently unspecified. Web search parser currently only accepts post SearchItem, so explicit review source needs root-owned presentation/read action changes. OpenAPI search response currently directly uses SearchResponseDataSchema and canonical query schemas.

## 4. Persistent schema change and maintenance facts

Current schema version is5. `packages/storage-sqlite/src/bootstrap.ts:classifyDatabase` permits only V5/V4/V3 table profile entries and the named post_fts virtual/shadow table family. Unknown added FTS tables classify unknown, not an optional cache. Current/legacy init and bootstrap migrate structure via strict profile checks. `src/schema.sql` is authoritative; `src/schema.ts` contains generated DDL and exact V1–V5 structures. `scripts/generate-schema.mjs` currently treats schema.sql as V5, reads frozen historical-v4/v3/v2/v1 fixtures; `check-schema-sync.mjs` repeats that profile model. A future schema6 needs preserved V5 source profile plus generator/check/bootstrap classification/version/migration handling; adding a virtual table in source without these contacts is insufficient.

`src/offline-upgrade.ts` permits source versions1–4, validates copied source before bootstrap, returns literal schema_version5. Schema5→6 requires this gate/result/source union to change. `src/offline-backup.ts` both implements backup and restore: manifest schemaVersion union2|3|4|5, defaults current5, emits5, strict parses supported versions and validates source profile; restore upgrades non5 copies via bootstrap then revalidates current. Physical backup copies all DB tables including derived state, so selected rebuild/sanitize handling must be compatible with this path. `resetRestoredIdentity` revokes credentials/rotates secret, not review text or FTS. Metadata-only recovery must not be mistaken for index privacy cleanup.

`src/space-export-snapshot.ts` enumerates public research families only, excludes formal review rows and private artifacts. `core/services/space-export-service.ts` emits formal_review_status/formal_check_status='excluded'. `src/logical-import.ts` consumes that existing public export into a newly bootstrapped isolated instance and rebuilds post_fts from imported current readable revisions; formal review records/eligibility are not restored. A new derived table alone need not add export/import review families; their unchanged exclusion/empty-table behavior must be verified. Adding opinions to export/import would be a separate contract expansion, not mandatory for search.

Minimum product ownership for a selected persistent scheme includes: protocol search/response guards/openapi (and tools/client/CLI/Web if explicit entry exposed); core storage port/search service/search cursor and whichever core visibility helper/redaction hook root selects; module submission service for reveal projection; SQLite sqlite-storage/schema.sql/schema.ts/bootstrap/offline-upgrade/offline-backup; generation/sync scripts; new frozen historical-v5 fixture. Existing export/import implementation files are read/verification contacts, not automatically mandatory edits if exclusion stays. Core/protocol export DTO changes would only be needed if root separately changes exported families. Schema/maintenance tests and exact old profile fixtures must be explicitly owned in the task, never silently rewritten as current fixtures.

## 5. Two implementation fact-costs, without selection

Persistent public FTS: existing post FTS shows the transaction/search machinery, but there is no formal index/reverse-ref table, reveal-index insertion port, historical material invalidation port or evidence reverse port. It would require schema/profile/offline upgrade and backup/restore handling above, atomic reveal insertion and every relevant public/private redaction deletion, and current read privacy checks to fail closed against corrupt/stale index records. Rebuild/backfill for existing schema5 revealed history would need intrinsic+online privacy gating; copying all payload_json or accepting revealed_at alone is not current public-read equivalence. Which payload fields/snippet/filters belong in FTS is not yet chosen.

Bounded derive-on-read: avoids an added durable search table, so no derived text remains to purge and reveal/redaction facts are immediately reflected inside a single read snapshot. However current storage only lists submissions per request; no space-wide ordered revealed metadata candidate iterator, cap/preflight/page port or matching snippet DTO exists. Existing per-row validation repeatedly reads request/snapshot/assignment/submission facts, bounded within a fixed request but potentially expensive across candidates. A SQL JSON scan must count/stop candidates before materializing payloads, exclude sealed rows before text/projection, retain current ACL/privacy per candidate and define pagination when redacted/invalid candidates are skipped; the current searchPosts preflight cannot be assumed to provide these. In-memory string matching lacks existing FTS phrase/token/snippet semantics. Neither bounded row count nor current output bytes proves hard CPU/memory/VM bounds. No implementation is selected here.
