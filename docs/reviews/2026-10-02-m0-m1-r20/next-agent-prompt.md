## 1. R20-F01：把已启用请求边界补完整，并保持正常调用

### 1.1 当前 32 个业务路由逐项清点

本目录 route-inventory 捕获 32 个 `/api/v1` 操作和一个自动 OPTIONS；19 个业务入口已有 body schema。不要仅给几个新路由补判断便宣布“全路由严格验证”。建立当前实际路由表，列 body/query/params/业务 header、schema 来源、缺省/空值/重复值及无该参数时的行为。

protocol 是唯一公共 schema 来源；传输层可有明确的 URL 字符串→领域值转换，但先验证，再交业务层。保留 body 的 `coerceTypes: false`，不靠全局强制转换使数字字符串、布尔字符串或坏 body 通过。params 的约束按现有 ID/枚举契约，不发明新的 ID 格式或提前实现分页协议。

### 1.2 必须关闭 AC01 的具体输入

| 输入/调用 | 要求 |
|---|---|
| `GET /spaces?bogus=1` | 400，未知业务属性不能静默忽略 |
| `cursor=a&cursor=b` | 重复标量拒绝，不能把数组传给 SQLite |
| 搜索 `tags=a&tags=b` | 当前 tags 为 CSV 传输参数，明确拒绝重复值；不对数组直接 `.split()` |
| 主题列表 `state=not_a_state` | 拒绝非法 ThreadState，复用公共定义 |
| 帖子 `revision=` | 明确拒绝；只有 undefined/真正省略采用默认版本，不能将显式空串默认为当前版 |
| membership 引用不存在的 actor | 稳定 4xx，无成员/事件/幂等写副作用；不靠外键错误变成 500 |

HTTP 框架的已知解析/输入错误应保持 4xx；不把任意内部异常原样暴露，也不把所有异常一律 400。对已知框架错误使用稳定映射，真正内部故障仍按内部错误处理。

正常 Host/Accept/User-Agent 等头继续兼容；业务 Idempotency-Key 按当前契约校验并由适配器正确映射。不要为了统一表格给当前管理操作增加未经要求的幂等操作族，不改变 poll/ack/deactivate 的既定例外。权限、引用存在性、枚举与状态不变量继续在服务端共享业务路径处理；不在 CLI/MCP/Pi 各复制一套。

每类严格校验同时保留合法输入正例：正常讨论/修订/关系状态变更、有效 query、标准请求头、默认 poll。不能把既有工具会传的参数统统拒绝而不修它们的映射。

## 2. R20-F02/F03：成功响应与错误分类

### 2.1 已知响应字段按 API v1 校验

保留 U06 截断 JSON reject，并关闭 AC02：

- `api_version` 必须符合本请求使用的 API v1；不是任意字符串。
- `request_id` 按现有协议必须是字符串；仅检查属性存在不足以拒绝 null/对象。
- 区分缺少 data 与具体操作允许的 falsy data；保留未知扩展属性的向前兼容。
- 同时含业务 error 与 data 的成功响应不得作为普通成功结果返回；error 是已有协议字段，不是可无条件忽略的未知扩展。
- 请求成功但 JSON/响应结构不合法时，用客户端解析/协议错误表示。不得伪装成服务端发来的 status 200 / VALIDATION_ERROR 输入错误。可用小型本地 Error 类或稳定 kind 判别；无需增加服务器错误码体系。

不要把所有 API 的业务 data 都放宽成任意值；也不要用闭合的请求 schema 拒绝响应的未知字段。按现有 wrapper 与公共协议需要做必要校验，范围限已启用能力。

### 2.2 分类不依赖 message

删除 `err.message?.includes('aborted')` 等猜测。AC03 中未取消的 409 REVISION_CONFLICT，即使 message 含 aborted，也必须保留业务 code/status/retryable/details。

服务端 DetunedError、用户取消、请求超时、传输错误、客户端响应解析/协议错误，至少能通过稳定类型或字段区分。分类依据自身 signal/timeout 原因、已识别的错误对象，不能把没有用户取消的 AbortError 或任意错误文本一概写成用户取消。

保留当前成功的外部 signal 贯穿及清理，不把服务器提交是否完成与客户端取消混为一谈。CLI 失败非零、MCP 工具失败、Pi execute 抛错；在正式测试里经过至少一个真实注册的工具回调验证坏响应和业务错误，不只直接调用 client。

## 3. R20-F04：有界重试与生命周期

1. 明确传输错误 allowlist 和错误原因读取，处理受支持的 fetch `TypeError.cause.code` 等实际形状；不能只看顶层 `err.code === 'ECONNREFUSED'`。不把所有 TypeError 都当网络错误。
2. HTTP/业务不可重试类别优先，400/401/403/404/409/413/422 等不能因 body 的 `retryable: true` 自动重发。重试不是让不合规错误响应变成功的机制。
3. 对 429/503 等受支持重试情形处理合法 Retry-After（秒数/HTTP 日期），不能早于服务器允许的时间发送。超出本地等待预算时可以明确停止自动重试，不能把 60 秒提示静默压缩成 1 秒。非法提示按明确的有界后备策略处理。
4. 沿用最多 3 次重试可行，但须在 docs/04 和测试写清“初次请求 + 最多 3 次重试 = 最多 4 次尝试”；若另选上限，保持 `maxRetries` API 含义一致，不靠硬编码测试数字掩盖差异。
5. 每次写入尝试使用最初 request_key；取消不再重试；解析/协议失败不盲目重试。超时是否允许自动重试按明确策略记录，不能隐含改变 key。
6. 明确 timeout 作用范围。每次 response body 消费完成/失败后，及时清理本次请求 timer/listener，再进入独立退避；正常退避、退避取消、成功或耗尽后都释放自己的资源。可以用一个小 helper 消除两段重复等待逻辑，不需要通用任务调度框架。

正式测试用可控时钟/阶段屏障记录计划延迟和调用次数，不实际等待 60 秒。验证网络恢复、503/Retry-After、不可重试 400、正常退避结束、取消退避、超时与用户取消分类、重试耗尽及固定键。资源断言须实际检查 listener/timer 或注入资源句柄，而不是完成后调用一次 abort 就写“无泄漏”。
