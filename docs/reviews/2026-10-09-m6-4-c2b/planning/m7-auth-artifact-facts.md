# M7.1 authentication/artifact facts (B read-only inventory)

This is current-code fact inventory for root task decomposition, not a selected M7 design/schema/permission route. Only this planning file is written; product/CLI/tests remain frozen. No build, test, runtime, host, browser, model or global/environment operation. No historical review inventory searched.

## Credential identity, persistence and ordinary authorization

- `packages/protocol/src/actors.ts`: ActorKind human|agent|service; CredentialCapability read|write|admin. Credential requires id/actor_id/token_hash/allowed_space_ids/capabilities/expires_at/revoked_at/created_at. There is no `CredentialScope`, check-run scope, verifier-only capability or canonical token-value structure/schema. `MeResponseSchema` advertises current actor/capabilities/allowed spaces/visible memberships.
- `packages/protocol/src/spaces.ts`: SpaceRole observer|contributor|maintainer|owner; Membership separately stores active/reviewer_eligible/independence_group. CheckProfile stores verifier_actor_ids/config_sha256/description, not verifier credentials or run authorization. `modules/review/src/index.ts` snapshot creation freezes sorted named profiles plus verifier actor IDs; `ReviewSnapshotManifestSchema` in protocol/review.ts bounds names32/IDs128 and snapshot records validate frozen profile consistency. These are existing configuration/manifest fields, not an implemented verifier gate.
- `packages/protocol/src/admin.ts`: CreateCredentialRequest only actor_id and optional allowed_space_ids/capabilities/expires_at. Its capability enum cannot express a run-only credential. Existing request/response guards and OpenAPI derive from these canonical schemas; new scope would touch schema/type, issuance validation, persistence decoding and auth consumers, with precise owner/API/compatibility chosen by root later.
- `packages/core/src/services/admin-service.ts` `createCredential`: `requireInstanceAdmin`, actor existence, rate limiter, random `detuned_tok_` plus24 random bytes hex; persists SHA256, defaults allowed_space_ids=['*'], capabilities=['read','write'], expiry null. `revokeCredential` is instance-admin-only and sets revoked_at. `/admin/credentials` POST in server/routes/admin.ts uses strict CreateCredentialRequestSchema and returns one-time raw token; no ordinary participant self-issuance endpoint. Membership mutations require space owner via shared business AuthService.
- `packages/storage-sqlite/src/bootstrap.ts` bootstrap issues `detuned_adm_` plus24-byte hex token for human admin, ['*'] and read/write/admin; this is current admin initialization, not a run token route. `sqlite-storage.ts` findCredentialByTokenHash/findCredentialById decode JSON allowed_space_ids/capabilities and nullable expiry/revoke; createCredential persists these columns. No scope column/property or guard conversion exists. Existing arbitrary legacy credential token prefixes remain accepted by hashed lookup: `AuthService.authenticateToken` does not parse or require a prefix, only trims and hashes the supplied raw token. Thus prefix naming alone cannot isolate a verifier.
- `packages/client/src/local-token.ts` tokenValue trims, rejects internal whitespace/control chars; bounded64KiB strict UTF8 regular-file read. CLI token-source reuses local input selection. This is local source hygiene, not server run-scope auth. `packages/server/src/app.ts` preHandler parses `Bearer ` and calls authenticateToken, attaches AuthenticatedContext; anonymous capabilities/health/static exceptions do not confer research permissions.
- `AuthService.authenticateToken` checks stored revocation, expiry and disabled/missing actor. `refreshContext` reloads credential by ID and actor, verifies credential actor binding, revoked/expiry/disabled; async committing services such as ArtifactService repeat it. Current expiry comparison is stored ISO string `< clock.nowIso()` (equality itself is not expired here); it is not a new run expiry algorithm. No stricter scope/lifecycle check is present.

## Isolation gaps a restricted verifier design must resolve

`AuthService.requireSpaceAccess` applies space existence, token allowed_space_ids ('*' or exact space), active membership, role hierarchy, and read/admin; writes additionally require write/admin. Admin gets virtual owner only if membership absent, still after allowed-space check. No run/request/snapshot restriction is inspected. Simply giving a verifier standard read/write plus a membership grants generic research operations according to role; a run ID in token name or Artifact.check_run_id is not consulted. Conversely missing read cannot enter current general space services; this does not provide the required scoped check-upload/receipt path today.

Exact isolation-sensitive consumers:

- core/services/auth-service.ts `requireSpaceAccess`, `requireInstanceAdmin`, `refreshContext`, `getMe` (the latter lists identity/visible-space metadata without a read-capability gate);
- server/routes/spaces.ts GET `/spaces` directly calls storage.listVisibleSpaces with actor/allowed-space IDs; it does not call requireSpaceAccess/capability gate. A future run credential must not accidentally inherit space-directory visibility just because this path uses standard context;
- generic post/revision/thread/context/search/event/export services use current space ACL; none recognize restricted verifier context. Current review getters reuse ordinary read plus own-or-revealed gates, not a run boundary;
- core/services/review-artifact-access.ts `assertReviewArtifactReadAccess` uses actor assignment ownership or a revealed submission that explicitly cites private artifact. A verifier credential sharing that reviewer actor and standard read would qualify by actor identity; there is no credential-scope veto. An admin credential does not bypass sealed ownership through this helper, but is otherwise broad and must not be supplied to an external verifier;
- backend WebSessionService login currently accepts human identity after authenticateToken and later refreshes it. This is an existing alternate auth-context consumer, not a request to modify frontend; scoped credentials must not gain general permissions by conversion to another context. Server mixed Bearer/cookie restrictions remain existing behavior;
- admin issuance/revocation and operations diagnostics require admin; generic admin capability is not a narrow check permission. Existing policy verifier_actor_ids is a frozen eligibility list only, not an implemented control against generic routes.

These identify exact boundary categories, not a chosen universal block, new role or token format. Scope isolation must be in service business auth as well as transport; CLI/MCP do not replace it. Root must decide backward-compatible canonical/legacy representation, trust and current-vs-frozen verifier revocation semantics before ownership/implementation.

## Existing artifact upload, download and storage mechanics

`protocol/artifacts.ts` Artifact has nullable check_run_id but visibility only space|review_assignment. Public ArtifactMetadata excludes check_run_id/internal storage_key; ReviewArtifactMetadata adds review_assignment_id, with strict ReadableArtifactMetadata union and isReadableArtifactMetadata/date guards. CreateArtifactMetadata allows only optional visibility:'space'. No check log metadata variant/binding guard exists.

`storage-sqlite/schema.sql` artifacts.check_run_id TEXT exists; SqliteStorage.createArtifact/findArtifactById preserves it. There is no check-runs/receipts entity/port to resolve that value or enforce its source. ArtifactService always writes check_run_id:null. The existing nullable column alone is not an authenticated run/log binding.

## Missing check-run, log and receipt source binding

`protocol/review.ts` already defines CheckRunResult pass|fail|error and SubmitCheckReceipt fields receipt_id/observed_snapshot_sha256/observed_check_config_sha256/result/environment/execution_steps/exit_code/logs_artifact_id. There is no CheckRun record/lifecycle/attempt model or StoragePort receipt methods in current inspected code. No service verifies logs_artifact_id belongs to a fixed run/verifier/snapshot/config or accepts a receipt. No HTTP/CLI/MCP implementation for these schemas is present.

`core/services/review-status-facts.ts` frozen required_checks empty→not_required, otherwise pending. `modules/review/src/finalization-service.ts` accepted with any required check throws REVIEW_INCOMPLETE; decisions always check_receipt_ids:[]; finalization/idempotency/events commit together. `core/services/review-decision-records.ts` immutable decision binding and `idempotency-service.ts` result reference validation are existing audit/replay patterns, not check receipt integration. Root must determine run/attempt immutability, selected latest attempts, verifier trust/scope, log source binding and transaction/replay safety before implementing; this note selects none of those policies.
