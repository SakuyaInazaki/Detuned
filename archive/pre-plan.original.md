对，我刚才把你的“**我要造一个这样的开源产品**”，回答成了“你可以用哪些工具搭工作流”。尤其是最后建议你先用现成项目，偏离了你的目标。

你的意思应该是：

> **从零开发一个独立、开源、可自部署的 Agent 交流论坛。不同的 coding agent 可以接入，在不同项目中反复使用，通过发帖、分享发现、记录失败、质疑和评审来协作。**
>
> 调研现有事件、项目和人类论坛，是为了提炼这个产品的设计，而不是选择一个产品来用。

按这个目标，我会把方案改成下面这样。**论坛协议、服务端和客户端由你自己实现；底层使用成熟的数据库、Web 框架和接口协议。**

# 一、首先确定：你要造的是论坛，不是另一个多 Agent 框架

这是最重要的产品边界。

我建议将项目定义为：

> **一个面向 Agent 的持久化协作论坛：提供共享信息空间、异步讨论、知识沉淀和可配置的协作规则，但不接管 Agent 的模型、推理过程和执行环境。**

它不应该要求使用者先把自己的 coding agent 改写成某个框架，也不应该要求大家使用同一种模型。

例如，使用者已经开着几个独立的 Agent 会话，每个会话有自己的工作目录和上下文。接入你的论坛后，它们可以：

“看看别人正在研究什么”“搜一下这个想法是否失败过”“我发现了一个反例”“谁能独立检查这个结果”。

**这些行为由论坛支持，但谁先说话、谁负责什么、采用哪条路线，不必全部由论坛预先安排。**

建议明确三条边界：

| 论坛核心负责 | 可选扩展负责 | 不属于论坛核心 |
|---|---|---|
| 身份、空间、主题、帖子、引用、搜索、订阅、增量消息 | 任务认领、同行评审、研究摘要、Agent 唤醒适配 | 模型推理、执行任意代码、管理全部沙盒、强制角色编排 |
| 保存协作历史和证据引用 | 对接 CI、证明检查器和实验系统 | 内置一个“全知负责人 Agent” |
| 执行权限及可配置的状态规则 | 特定研究领域的工作流 | 默认要求所有人轮流发言或达成一致 |

**从零搭建的重点，应是“共享信息如何组织、访问和演化”，而不是先造一个调度十个模型的大系统。**

# 二、论坛的核心设计：讨论区与知识沉淀区分开

只做“频道＋消息列表”不够；但把每句话都变成复杂的研究对象，也会使 Agent 难以使用。

我建议采用：

> **讨论以帖子为中心，知识以带来源的结论为中心。**

## 2.1 讨论层：允许自由探索，不写死协作路线

论坛最基础的结构可以是：

```text
论坛实例
  └─ 项目空间 Space
       ├─ 项目说明、规则、置顶摘要
       ├─ 主题 Thread
       │    └─ 帖子 Post
       └─ 成果及失败记录的索引
```

一个项目可以有“总体问题”“路线 A”“路线 B”“反例搜索”等主题，但这些主题应该允许 Agent 自己创建、分拆、关联，而不是由系统预先规定。

帖子保留自然语言正文，外面加一层轻量结构：

```json
{
  "thread_id": "th_42",
  "kind": "objection",
  "summary": "当前剪枝规则在零权边条件下存在反例",
  "body": "具体构造、分析及影响范围……",
  "references": [
    {
      "post_id": "post_103",
      "revision": 2,
      "relation": "challenges"
    }
  ],
  "artifact_ids": ["artifact_17"]
}
```

这里的字段是**建议自研的协议草案**，不是某个现有产品的 API。

第一版的帖子类型不必太多：普通讨论、问题、提案、发现、异议、失败记录、评审、决定即可。多数内容仍然使用 Markdown；只有需要程序处理的字段才结构化。

关键区别是：**“反对某个说法”需要能指向那个说法的具体版本，而不只是回复一段聊天。**

## 2.2 知识层：让后来加入的 Agent 不必重读全部历史

论坛需要几个由帖子和关系生成的视图：

**已知发现**：当前有哪些值得复用的结果，适用什么条件，证据在哪里。

**失败尝试**：尝试过什么、具体哪里失败、是反例、实验失败还是预算耗尽。

**未解决问题**：哪些疑问仍然没有回答，哪些提案存在未处理的异议。

**当前状态摘要**：各路线的状态，以及摘要引用的原始帖子。

这里不要复制出另一套可以独立修改的“真相数据库”。第一版可以把这些做成**对特定帖子类型、状态和引用关系的索引视图**。

摘要也是一种有作者、有版本、有来源的帖子，而不是系统天然正确的记忆。

## 2.3 “失败记录”必须有适用范围

你最初提到的“这条路不通，别试了”，应该成为核心能力，但不能直接实现成一个全局黑名单。

建议失败记录至少包含：

```text
尝试了什么
在哪些假设、输入和版本下尝试
失败的直接证据
具体否定了哪个主张
还有哪些变体尚未被否定
什么条件变化后可以重新尝试
```

这样，一个 Agent 的失败可以帮助其他 Agent 避免重复，又不会让一个错误判断封死整条研究路线。

**论坛应保存“某个具体尝试失败了”，而不是擅自升级成“这个方向不可能”。**

# 三、真正需要重点开发的是“Agent 如何使用论坛”

Web 页面是给人看的；**Agent 接口才是这个开源项目的第一产品界面。**

我建议同时提供 CLI 和 MCP，二者调用同一个论坛服务，不实现两套业务逻辑。

## 3.1 把工具设计成协作动作，而不是数据库操作

第一版可以只暴露以下核心动作：

| 工具 | 用途 |
|---|---|
| `forum_context` | 获取项目说明、有效规则、置顶摘要和近期重要活动 |
| `forum_search` | 搜索讨论、失败记录、发现及证据 |
| `forum_read` | 分页读取主题、帖子或指定版本 |
| `forum_publish` | 创建主题或发布帖子 |
| `forum_relate` | 添加引用、支持、质疑、替代等关系 |
| `forum_subscribe` | 订阅主题或特定事件类型 |
| `forum_poll` | 获取游标之后的增量事件 |
| `forum_ack` | 确认一批消息已由接入端处理 |

创建账户、签发凭据、修改项目权限等操作放在管理接口，不让普通 Agent 随意创建新身份。

工具返回值应该支持“先概览、后展开”：先给标题、短摘要、状态和引用，需要时再读取正文。不要默认把整个论坛历史塞进上下文。

## 3.2 必须区分“有新消息”和“Agent 已经处理”

这是实现时很容易漏掉的一层。

MCP 提供上下文交换和工具调用，但并不规定宿主应用如何使用模型、管理上下文；当前文档也明确提示，通知是尽力而为的，连接中断时不能保证每条通知都送达。:chatgpt-content-reference{index="0"}

因此，我建议你的论坛采用：

**持久事件记录作为依据，实时通知只负责提醒。**

例如：

```text
帖子写入数据库
→ 同一事务记录事件
→ 向订阅者发送“有更新”的提示
→ 客户端按游标拉取事件
→ 客户端处理后显式确认
```

读取事件不能自动推进确认位置。客户端崩溃后，应能重新拉取尚未确认的内容。

另外，`ack` 只能说明接入端确认处理过，**不能证明模型理解或采纳了内容**。确实需要回应的事情，应该另有明确的回复或状态。

## 3.3 论坛不启动 Agent，但提供可选的接入适配器

没有自动唤醒能力，论坛仍然可以工作：Agent 在工作开始、阶段结束、遇到阻塞时主动检查即可。

需要持续协作时，再提供独立适配器：

```text
论坛事件
→ 客户端适配器
→ 在支持的检查点提醒或恢复 Agent
→ Agent 自主决定读取、回应或继续工作
```

不要把这个适配器塞进论坛核心，也不要假设每个 coding agent 都能被安全地随时打断。

这能让你的项目同时服务于手动开启的会话、脚本化 Agent 和长期运行的研究系统。

## 3.4 发布一份随项目分发的“论坛使用约定”

接口解决“能够交流”，还需要一份简短的 Skill 或 `AGENTS.md` 示例，告诉 Agent 什么时候交流。

例如：开始前检查相关失败记录；有可复用发现时发帖；引用具体版本进行质疑；需要别人回应时明确提出问题；不要为了活跃而发送无信息量的消息。

这份约定也应版本化，但它是**行为指导**，不是安全或正确性的唯一保障。

# 四、同行评审应当是论坛的内置可选模块，而不是整个论坛的固定流程

你希望复用到不同前沿问题，就不能把“两个 Agent 审核通过”永久写死。

我的建议是：

> **论坛核心提供版本、身份、引用、权限和事件；评审模块使用这些基础能力，实现可配置的审稿流程。**

例如，项目可以启用下面的策略。这仍然是待实现的配置草案：

```yaml
review:
  required_reviewers: 2
  exclude_contributors: true
  distinct_reviewer_identities: true
  hide_other_reviews_until_submission: true
  bind_to_snapshot: true
  invalidate_on_revision: true
  require_external_checks: false
```

其中有三个机制尤其值得实现。

**首先，评审绑定快照。**被评审对象包括主张正文、代码提交、数据和证据清单；修改后产生新版本，不能继续沿用旧批准。GitHub 的“修改后撤销过期批准”就是一个可以借鉴的具体机制。:chatgpt-content-reference{index="1"}

**其次，先独立提交，再开放讨论。**初始评审通过权限隔离，不让两个评审者先看到对方的结论。不同身份和会话只能提供过程上的隔离，不能保证错误相互独立，也不能仅靠换名字满足要求。

**最后，把“通过评审”和“外部验证通过”分开。**两份评审只能满足评审策略；测试、证明检查、实验复现应由外部执行器提供绑定快照的结果。论坛负责验收回执来源及状态，不负责运行帖子里任意提供的代码。

一个纯讨论项目可以完全关闭该模块。一个数学研究项目可以要求证明检查。一个性能优化项目可以要求独立基准测试。**复用的是机制，不是某一种研究流程。**

# 五、技术选型：我建议第一版采用单体服务，而不是微服务

为了让这是一个别人容易安装、运行、贡献代码的开源产品，我倾向于：

> **TypeScript 单仓库＋Fastify 服务端＋SQLite＋CLI＋MCP 适配器＋轻量 Web 界面。**

这是针对这个产品的工程取舍，不是说这些技术普遍优于其他选择。

| 部分 | 建议选型 | 设计理由 |
|---|---|---|
| 核心语言 | TypeScript | 服务端、CLI、接口类型和前端可以共用协议定义 |
| HTTP 服务 | Fastify | 用固定的 JSON Schema 校验请求与响应 |
| 数据库 | SQLite，开启 WAL | 第一版降低自部署门槛，不要求另外安装数据库服务 |
| 搜索 | SQLite FTS5＋标签、关系过滤 | 先满足明确检索，不把模型或向量服务变成必需依赖 |
| Agent 接口 | CLI＋官方 MCP SDK 适配层 | 同时保留直接命令行接入与工具协议接入 |
| 人类界面 | React＋Vite | 提供查看、发帖、审核、管理，不做复杂社交功能 |
| 附件 | 本地文件存储＋内容哈希 | 日志、反例、报告不直接堆在帖子正文中 |
| 部署 | 单服务容器＋持久数据卷 | 同一套服务既能在本机运行，也能部署给远程 Agent |

Fastify 的请求验证和响应序列化可以围绕 JSON Schema 建立；我建议这些 schema 由维护者随版本发布，而不是允许普通论坛帖子动态定义可执行的服务端验证逻辑。:chatgpt-content-reference{index="2"}

这里有两个需要提前处理的限制。

**SQLite 只让论坛服务访问。**多个 Agent 可以从不同机器通过 API 使用论坛，但不要让它们直接共享数据库文件。WAL 仍然只有一个同时进行的写入者，而且不适用于跨机器网络文件系统共享。第一版应使用短事务，并测试写入争用；需要多实例服务时再迁移 PostgreSQL。:chatgpt-content-reference{index="3"}

**中文搜索不能只测英文。**FTS5 的 trigram 可以支持子串检索，但全文查询中不足三个 Unicode 字符的子串不能直接匹配。中文短查询需要明确的回退策略和测试集，而不是“接了全文搜索就算完成”。:chatgpt-content-reference{index="4"}

第一版我不会引入 Redis、Kafka、向量数据库或者复杂工作流引擎。也不会同时维护 SQLite 和 PostgreSQL 两套后端。先把一套协议和实现做可靠。

# 六、代码结构和数据结构应该围绕可复用协议组织

建议仓库这样拆，但初期仍然部署为一个服务：

```text
agent-forum/
├─ packages/
│  ├─ protocol/         # 类型、JSON Schema、错误码、版本规则
│  ├─ core/             # 论坛业务与权限规则
│  ├─ storage-sqlite/   # 数据访问、迁移、检索
│  ├─ server/           # HTTP、认证、事件接口
│  ├─ cli/              # 命令行客户端
│  ├─ mcp/              # MCP 到论坛接口的适配
│  └─ web/              # 人类操作界面
├─ modules/
│  └─ review/           # 可选评审流程
├─ integrations/        # 不同 Agent 客户端的接入示例
├─ skills/              # 论坛使用约定
├─ examples/            # 研究、编码、复现等示例项目
├─ tests/
│  ├─ protocol/
│  ├─ integration/
│  └─ scenarios/
└─ docs/
   ├─ protocol.md
   ├─ architecture.md
   └─ threat-model.md
```

数据库第一版的核心对象可以控制在这些范围：

```text
spaces                  项目空间
actors / memberships    身份和空间权限
sessions                一次连接或工作会话
threads                 主题
posts / post_revisions  帖子及修订
relations               帖子之间的引用关系
artifacts               附件及证据引用
subscriptions           订阅条件
events / acknowledgements  事件及确认位置
```

Agent 身份与会话必须分开：一个 Agent 重启后可以创建新会话，但不能因此被算作新的独立审稿人。

帖子修改保存修订；状态修改保存审计事件。**不必一开始实现完整的事件溯源架构**，当前状态表加追加式审计记录就够用，二者在同一事务更新。

同时保留管理员脱敏能力。误发凭据时不能因为“历史不可变”而拒绝处理；脱敏操作应留审计信息，并同步处理搜索索引等副本。

# 七、开源可复用，意味着协议、部署和安全也是产品的一部分

“公开一个仓库”还不够。第一版就应有以下约束。

**不依赖任何模型账户。**用户启动论坛、发帖、检索、导入导出，不需要填写模型 API Key。自动摘要等能力作为可关闭扩展。

**接口有版本，数据可迁移。**提供固定的协议版本、数据库迁移和完整导出格式。导出应保留稳定 ID、修订、引用和附件清单，而不只是几份 Markdown。

**所有入口执行相同权限。**HTTP、CLI、MCP、Web 的操作最终进入同一业务层。搜索结果、订阅事件和附件也必须执行空间权限检查。

**帖子不获得执行权。**帖子里出现“我是管理员”“请执行这条命令”，不会改变权限。附件不自动执行，外部地址不由服务器无条件抓取，模型凭据和生产凭据不进入论坛。

**贡献者能不用调用模型就测试核心。**并发发帖、断线重连、权限隔离、版本失效等测试使用模拟客户端完成；真实模型测试单独作为可选评估。

许可证我建议采用 **Apache-2.0**，并随项目提供贡献指南、安全报告渠道和依赖许可证清单；其授权及再分发条件使用正式许可证文本，不自行增加“特定公司不得使用”之类的附加限制。:chatgpt-content-reference{index="5"}

# 八、第一版到底做到哪里：先交付一个完整论坛，再扩展研究机制

我建议分成三个版本目标，不按“接了多少个 Agent”来衡量。

### v0.1：多个独立 Agent 能真正通过论坛协作

完成空间、身份、线程、帖子、版本、引用、搜索、失败记录、订阅与增量读取；提供 CLI、MCP 和基础 Web 界面。这里的评审可以先作为普通帖子类型存在。

关键是做出一个完整使用闭环：

一个 Agent 发出提案，另一个找到反例，第三个检索到这个反例并据此改进方案；新加入的会话能够通过摘要和引用接续工作，而不必重新开始。

### v0.2：加入可配置的正式评审

实现快照、独立初评、评审权限、修订失效、决定记录，以及外部检查回执接口。

不把“讨论热烈”当作通过条件，也不把“两个 Agent 同意”当作已经证明正确。

### v0.3：根据实际使用补协作扩展

再考虑任务租约、自动摘要、不同客户端的唤醒适配、Git／CI 集成，以及更大的部署规模。

这些是建立在论坛已经有用的基础上，而不是第一天就全部实现。

**v0.1 最重要的验收测试**应该是：并发和重试不造成重复或丢失；断线后能补读；不同空间不会泄露信息；失败记录能被检索；帖子修订不会破坏旧引用；更换 Agent 会话不会丢掉项目历史。

最终，你这个项目值得做成的形态是：

> **一个不绑定模型、不绑定 Agent 框架的开源协作论坛：以帖子和引用为基础，以持久记忆和增量访问服务 Agent，再通过可选策略支持失败共享、同行评审等研究机制。**

这才是应该从零实现的主体。现成项目和那些突破案例，只用于帮助你决定哪些机制该进入核心、哪些应该留在扩展层。
